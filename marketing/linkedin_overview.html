THE PROBLEM

Five teams, five dashboards, one customer

A Sales rep checks pipeline in one report. PreSales pulls deal detail from another tab. Marketing builds a campaign ROI dashboard. Support triages a case queue. Customer Success cross-references renewal and case reports by hand every Monday morning. All five are describing the same underlying Salesforce org — just through different, disconnected views of it.

Every one of those views takes a login, a click path, and a mental switch away from the actual conversation someone's trying to have — with a customer, a manager, or a teammate.

This project asks a simple question: what if the CRM answered you directly, in plain language, inside the conversation you're already having — instead of the other way around?

Salesforce Cloud MCP Server 02
THE SOLUTION

One MCP server, two ways to run it

Built on Anthropic's Model Context Protocol — an open standard for connecting an AI assistant to real, live data. Claude doesn't get a snapshot or a training-time guess about your Salesforce org; it calls the same REST API your browser does, with your own OAuth session, in real time.

Salesforce Cloud MCP Server 05
WHAT YOU CAN ACTUALLY ASK — CUSTOMER SUCCESS

The relationship side, not the ticket side

Support answers "what's open right now." Customer Success answers "who's about to churn." Different job, different tools — even though both live on the same Case object underneath.

Customer Success

  • Open renewals in any window you name — this quarter, next 60 days, whatever matters
  • At-risk accounts — low-probability renewals cross-referenced with open high-priority cases, ranked by deal size, so you know who to call first
  • A fast health check on one account — case load, last logged activity, open opportunities — before you pick up the phone
“Which accounts are at risk in the next 60 days?”
“What's renewing this quarter?”
“Give me a fast health check on this account before I call them.”

Every tool is documented for what it's built on — standard Salesforce fields where possible, with a clear note on where an org's custom fields (health score, NPS, renewal risk) need one small addition. The project ships with a contributor's guide for exactly that.

One thing worth being explicit about: the function pages in this deck are organizational, not a permission boundary. A Customer Success person can call Support's sf_create_case or PreSales' sf_update_contact just as easily — every tool is available in every conversation.

Salesforce Cloud MCP Server 07
ONE ASK, MULTIPLE TOOLS

The real unlock isn't one tool — it's chaining them

Claude doesn't just call one tool per question. Ask something that spans a few systems, and it works out which tools to call, in what order, and stitches the results into one answer — no separate dashboards, no manual cross-referencing.

“Before my QBR with Acme Corp, give me the full account picture, check if they're at risk, and log a follow-up task.”
Chains sf_get_account_360 → sf_get_at_risk_accounts → sf_log_activity_note
“Pull our top campaigns by ROI this quarter, then tell me which of those leads are still open and unworked.”
Chains sf_get_campaign_performance → sf_get_campaign_members → sf_get_leads
“Summarize pipeline by stage, and log a note on any deal over $50k with no recent activity.”
Chains sf_get_pipeline_summary → sf_get_open_opportunities → sf_log_activity_note
“Check if this account is in our VIP segment in Data 360, and if their case volume is high, open a follow-up case.”
Chains dc_query → sf_get_open_cases → sf_create_case
“This account just escalated — check their case history, see if they're already flagged at-risk, and bump this ticket to Critical.”
Chains sf_get_open_cases → sf_get_at_risk_accounts → sf_update_case

HOW IT'S BUILT

Engineered to be extended, not just used

  • OAuth 2.0 Authorization Code + PKCE for Sales/Service Cloud — a real browser login, a refresh token, no hardcoded credentials anywhere in source.
  • A separate, correctly-scoped connection for Marketing Cloud — it's a genuinely different Salesforce product with its own API, and the code treats it that way instead of pretending it's the same system.
  • One tool file per business function (sales, presales, marketing, support, customer success) sharing a single generic SOQL/REST client — adding a new tool never touches auth or another team's file.
  • Read tools and clearly-marked mutating tools (update, create, and scoped delete operations), with the convention documented so anyone contributing keeps that split visible.
  • Two runnable entrypoints, one codebase — a stdio process for local use, a Streamable-HTTP service with a health check and access control for cloud deployment, sharing every tool and client underneath.
  • MIT licensed, with a contributor's guide, an environment template, and a fictional demo dataset so anyone can try the tool shapes before connecting a real org.
